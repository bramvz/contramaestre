# ADR-0001: Enforce prompt gates at agent level with single-use proof (2026-07-24)

**Status:** Proposed
**Scope:** `.contramaestre/hooks/handlers/user-prompt-submit.js`, `.contramaestre/hooks/lib/CheckinReminder.js`, `.contramaestre/hooks/lib/SkillGate.js` — the UserPromptSubmit prompt-gating layer

## Context
- Generated by background agent based on diff inspection + transcript.
- A code review of the `feat/checkin-plan-capture` branch surfaced two defects in the prompt-gating layer, both confirmed to be branch regressions absent from `main` (the SkillGate hole was only latent on `main` because the feature was inert there). This ADR records the enforcement model those fixes lock in, because the invariants involved are non-obvious and easy for future refactors to reintroduce.
- The check-in gate can refuse *every* prompt when a session has no (or a stale) check-in. A hard kernel-level rejection (`decision:block` / exit 2) silently drops the prompt with no visible agent reply, and — since the injected directive forbids tool use — even Claude could not invoke the check-in skill to clear the gate. Users who typed a documented invocation form (`check in`, `check-in`, a leading `continue`) were trapped, only escaping via exact `/checkin` syntax.
- SkillGate requires a UserPromptExpansion event as proof-of-invocation before opening a gate. A prior fix stamped `__lastExpansionAt` on every expansion (valid for a 10s promotion window) but never consumed it, so one expansion could vouch for multiple later submits — a plain prompt matching a gate's regex within the window opened the gate with no skill actually invoked, defeating the proof-of-invocation design.

## Decision
- Prompt gates enforce at the **agent level**: a triggered gate injects `additionalContext` directing Claude to refuse and explain this turn, rather than a hard block. The user's message survives in the conversation for retry after they satisfy the gate.
- Because a self-clearable soft gate demands it, the check-in exemption must recognize **all documented invocation forms** — `/checkin`, `checkin`, `check in`/`check-in`, and a leading `continue` — anchored at message start with word boundaries so non-invocations (`checking the logs`, `please continue`) still pass through to the gate.
- Invocation proof is **single-use**: each UserPromptSubmit consumes (`delete`s) `__lastExpansionAt` unconditionally — even when no rule matches — so one expansion vouches for at most the one Submit that immediately followed it.

## Alternatives
- Hard kernel block (`decision:block` / exit 2) — rejected because it produces no visible reply and cannot be self-cleared by invoking the skill.
- Exempt only slash syntax `/checkin` — rejected because it contradicts the skill's own documented natural-language triggers and traps users.
- Exempt `continue` anywhere in the prompt — rejected as too broad (a common plain instruction); only a *leading* `continue` is exempt, accepting `please continue` as a known gap.
- Consume the expansion stamp only on a rule match — rejected because a non-matching submit would leave a live stamp for a later matching submit to falsely consume.

## Consequences
- Benefit: gate refusals are visible and explanatory, prompts are retryable, and proof-of-invocation can no longer be replayed across submits.
- Cost: enforcement is advisory (depends on the model obeying the injected directive), not a guaranteed kernel-level block; the master log still labels these `gate:` as if hard.

## Guardrails
- Preserve: exactly one UserPromptExpansion may vouch for at most one immediately-following Submit — always consume `__lastExpansionAt` on every Submit.
- Preserve: the check-in exemption regex must cover every invocation form the check-in skill documents, or users get trapped behind the gate.
- Revisit when: the CLI gains a real user-visible hard-block mechanism, the Expansion→Submit ordering/timing contract changes, or the check-in skill adds/renames trigger phrases.
